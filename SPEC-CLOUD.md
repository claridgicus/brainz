# Brainz Cloud — free hosted knowledge graph on Cloudflare

Extends SPEC.md. Brainz Cloud hosts vaults for everyone, free: sign up, create a vault, point any orchestrator at a remote MCP URL. Local (packages/*) stays fully supported; cloud reuses the same engine.

## New layout

```
packages/engine/    # @brainz/engine    — PURE platform-agnostic logic (no fs, no better-sqlite3, no node-only APIs)
packages/contracts/ # @brainz/contracts — single source of truth for every wire shape (zod)
apps/cloud/         # SvelteKit app → ONE Cloudflare Worker: UI + REST API + remote MCP
```
Root workspaces become `["packages/*", "apps/*"]`.

## `@brainz/contracts` — wire-shape source of truth (zod)

Purpose: the MCP server, CLI `--json` output, cloud REST API, and web clients must never drift. Every shape that crosses a process boundary is defined ONCE here as a zod schema; TS types come from `z.infer`. Depends on `@brainz/engine` for domain types; pure/Workers-safe like engine (zod is the only extra dep).

- **MCP tool registry**: `MCP_TOOLS` — an ordered record of all 8 tools, each `{ name, description, inputSchema (zod object), outputSchema (zod) }`. Tool descriptions (the orchestrator-facing UX text) live HERE, not in the server. `@brainz/mcp-server` must build its tool registrations by iterating this registry — no hand-declared names/schemas left in the server. The remote MCP in apps/cloud iterates the same registry.
- **Tool outputs**: the JSON payload of each tool response is validated against its `outputSchema` in tests (server tests parse response text with the contract schema — that's the sync guarantee).
- **REST API schemas**: request/response zod schemas for every apps/cloud endpoint (vault, concept, key create/list, search, related, context, graph `{nodes, edges}` incl. `pending` flag, stats). The SvelteKit UI's typed fetch client imports these.
- **CLI `--json` shapes**: reuse the same schemas (search hits, show, related, context bundle, validate report, reindex/stats). CLI tests assert `--json` output parses with the contract schema.
- Versioned lightly: export `CONTRACTS_VERSION` string; bump on breaking shape changes.

Refactor obligations when this package lands: mcp-server derives registrations from `MCP_TOOLS`; cli imports output types + validates in tests; packages/web may adopt the graph/concept schemas where trivial (don't force it). Existing behavior/wire shapes must NOT change — encode what's already shipped.

### Storage architecture: one Durable Object per vault

**Vault content lives in a per-vault Durable Object (`VaultDO`) using DO SQLite storage (`ctx.storage.sql`).** D1 is only the shared control plane. Isolation comes from the DO boundary, not WHERE clauses.

**D1 (control plane, drizzle):**
- Better Auth tables (user, session, account, verification) — generated per Better Auth docs
- `vault(id pk, owner_id → user, slug, name, created_at)` — slug unique per owner; `id` is the DO name → `env.VAULT_DO.idFromName(vault.id)`
- `api_key(id pk, vault_id → vault, name, key_hash, key_prefix, created_at, last_used_at)` — token format `bz_<32 rand>`; SHA-256 hash at rest; plaintext shown exactly once at creation
- Dreaming spend controls: `dream_spend` (per-user, per-UTC-day ledger), `llm_key` (one AES-GCM-encrypted BYOK dream key per user), `control_flag` (operator kill switch) — see "Spend controls" under Dreaming

**VaultDO SQLite (data plane, per vault):**
- `concept(id pk, title, type, status, product, tags_json, body, hash, created_at, updated_at)`
- `edge(from_id, to_id, relation, src)` where src = 'wiki' | 'frontmatter'
- `embedding(concept_id pk, vector blob, hash)`
- FTS5 virtual table for concepts if DO SQLite supports it (verify at runtime/in dev!); otherwise fall back to a LIKE/token-based keyword search — hybrid still works via engine's RRF.
- Schema created/migrated idempotently in the DO constructor (`blockConcurrencyWhile`) with a `meta(schema_version)` row.

VaultDO exposes typed methods (RPC-style via DO class methods, or a fetch router — agent's call; RPC preferred on modern wrangler): `upsertConcept`, `deleteConcept`, `getConcept`, `list`, `search`, `related`, `graph`, `context`, `stats`, `destroy` (called on vault delete: `deleteAll` storage). All graph/search/context logic comes from `@brainz/engine`; the DO is storage + orchestration only.

Concept writes parse the submitted markdown body with engine's `parseNote` (wiki-links → edge rows, relations → edge rows) and re-embed via Workers AI (`@cf/baai/bge-base-en-v1.5`, 768-dim) when hash changes — the Worker passes an embed callback/result into the DO or the DO calls `env.AI` directly (bindings are available to DOs). If AI is unavailable (local dev without login, tests), degrade to keyword-only — mirror core's graceful fallback. Embedding failures must never fail the write.

### Remote MCP (`/mcp` route)

- MCP Streamable HTTP, auth: `Authorization: Bearer bz_...` → resolves vault via D1 key lookup, then routes into that vault's `VaultDO`; 401 otherwise. OAuth 2.1 access tokens (`bzat_…`) are accepted too, and a gated tool called with no token gets a 401 lazy-auth challenge: see "OAuth 2.1 for remote MCP (Wave OA)" below.
- Same 8 tools as SPEC.md (search_concepts, get_concept, get_related, get_context, upsert_concept, link_concepts, list_concepts, vault_stats), registered by iterating `MCP_TOOLS` from `@brainz/contracts`, backed by the VaultDO + engine.
- Implementation options (agent's call, in preference order): (a) Cloudflare `agents` SDK `McpAgent` — MCP server AS a Durable Object, the platform-native pattern; run it per-vault, or (b) stateless `@modelcontextprotocol/sdk` StreamableHTTP via a fetch-adapter (e.g. `@hono/mcp`) in the route handler that calls into VaultDO. Either way the agent verifies against a real MCP client call over HTTP in wrangler dev. If McpAgent fights SvelteKit route integration, (b) is fine — don't sink hours.
- Client wiring docs: `claude mcp add --transport http brainz https://<host>/mcp --header "Authorization: Bearer bz_..."` (and raw .mcp.json equivalent).
- **Discovery / advertisement (standards)**: the server is auto-discoverable — `static/.well-known/mcp.json` (and the SEP-1649 alias `static/.well-known/mcp/server-card.json`) serve a server-card document in the MCP Registry `server.json` schema (name `ai.brownmatter/brainz`, streamable-http remote at the production `/mcp`, `Authorization` header advertised as optional+secret since unauthenticated connections get the public toolset) plus a namespaced `_meta` block listing both toolsets, the signup/claim flow one-liner, and the `/skill.md` prompt URL. A registry publish artifact `apps/cloud/server.json` (same doc minus `_meta`; description ≤ 100 chars per registry cap) is published to registry.modelcontextprotocol.io under the DNS-verified `ai.brownmatter/*` namespace — runbook in apps/cloud/README.md. `discovery.test.ts` pins all three artifacts to the contracts registries (tool lists, SERVER_VERSION, production URL) so they cannot drift.
- **Grok Build plugin**: `integrations/grok-build/brainz/` is the source of truth for `external_plugins/brainz` in `xai-org/plugin-marketplace` (vendored local plugin: `.grok-plugin/plugin.json`, a `.mcp.json` pointing at the production `/mcp` with no headers, and a `brainz` skill). It authenticates with OAuth ("OAuth 2.1 for remote MCP" below) through Grok's built-in MCP OAuth client (DCR, PKCE S256, loopback redirect). Grok starts OAuth only when the *handshake* returns 401, and lazy auth lets the anonymous `initialize`/`tools/list` through, so Grok connects with the tool list and every call fails `Auth required` until the user presses `i` on the server in `/mcps`; the README and skill say so. Fallback for browserless runs: the user defines a same-named `brainz` server in their Grok config with `Authorization: Bearer ${BRAINZ_API_KEY}`, which replaces the plugin's server. No credential is bundled. The skill stays task-triggered (no "every session" steering) and never asks for a key or token in chat. Update flow: copy the folder into the marketplace fork, regenerate its index, PR.
- **Human-facing instructions**: the app splash (`/`) shows the endpoint + `claude mcp add` snippet and links `/.well-known/mcp.json`, `/skill`, and the marketing docs; the marketing `/docs` page keeps the full hosted + local wiring guide.

### Agent-driven signup over MCP (public toolset)

An orchestrator agent must be able to provision a workspace straight from the MCP endpoint — **without an email** — and the workspace only becomes permanent once a human approves attaching their email (see Wave G below, which supersedes this section's earlier email-at-signup + `claimUrl`/`loginUrl` designs):

- **Unauthenticated `/mcp/agent` connections** (`AGENT_MCP_PATH`) get a PUBLIC MCP server exposing exactly two tools, `signup` `{vaultName?, email?}` and `sign_in`. (Until the directory policy review this was unauthenticated `/mcp`; `/mcp` now hands out no API key, see "Directory policy" below.) `bz_` keys and public-vault tokens work on `/mcp/agent` exactly as on `/mcp`; OAuth access tokens are bound to the `/mcp` resource and 401 there, with a bare `Bearer` challenge (no `resource_metadata`, since `/mcp/agent` is not an OAuth protected resource). (Invalid/revoked bearer still 401s — only *absent* auth gets the public server.)
- `signup` creates a **provisional** account: a Better Auth user row with a placeholder identity (`unclaimed-<userId>@pending.brainz.invalid`, `emailVerified: false`, `expires_at = now + 7 days`), a first vault (default "My vault"), and an API key. Returns `{ apiKey: "bz_…", vaultSlug, expiresAt, claimEmailSent }` — NO login or claim URL is ever returned to the agent (a returned URL sits in orchestrator logs and proves nothing about a human).
- If `email` is supplied, it is NOT bound to the account — it merely triggers the same claim-request flow as the `claim` tool (Wave G), and `claimEmailSent: true` is returned regardless of the address's eligibility (no account-existence oracle).
- **Rate limiting**: per-IP (CF-Connecting-IP) counter, max 5 signups/hour — D1 `signup_events`; 429-style isError beyond it.
- Provisional accounts EXPIRE unclaimed: bearer auth (REST + MCP) rejects keys whose owner is past `expires_at` with a clear "workspace expired unclaimed — sign up again" message. Persistence requires the Wave G claim flow.
- Contract: the `signup` tool schema lives in `@brainz/contracts` as `PUBLIC_MCP_TOOLS` (same shape as MCP_TOOLS; NOT added to the vault tools — the local stdio server has no accounts). Docs (app MCP snippets + the self-onboard skill, Wave G) mention the flow.

### Onboarding (`onboard` tool + CLI command)

A vault must be onboarded before it's genuinely useful: onboarding = an orchestrator agent indexing an existing product's codebase into the vault. Brainz doesn't run agents itself — the `onboard` tool hands the CALLING agent a structured playbook and tracks completion.

- **The product ontology** (types grow to 10: add `domain`, `workflow`, `story`, `spec` — engine + contracts + core + DO + both UIs' palettes + docs):
  - `domain` — high-level product area ("Authentication", "Search"). The top of the graph; everything else hangs off domains.
  - `feature` — a concrete capability, `part_of` a domain.
  - `story` — a user story; the MAPPING facet between domains and features: story is `part_of` its domain and `realized_by` one or more features ("As a user I stay signed in across visits" → part_of Authentication, realized_by Session Refresh).
  - `spec` — technical specification: the RULES under which a function must be performed; a spec `governs` the features/stories/domains it constrains (e.g. "Session tokens rotate every 15 min" governs Session Refresh).
  - `workflow` — a multi-step user/system journey across features (`part_of` domain, `depends_on`/references features in order).
  - `concept` (generic), `decision`, `constraint`, `pattern`, `glossary` — as before.
  - Canonical relations grow: `realized_by`, `governs` join `depends_on`, `part_of`, `constrains`, `supersedes`, `related_to` (relations stay free-form strings; these are the documented conventions the playbook teaches).
- **Code areas**: optional frontmatter `code_areas: ["packages/core/src/vault.ts", "apps/cloud/src/routes/api/**"]` — rough paths/globs telling a coding agent where in the codebase this knowledge lives. Additive `codeAreas?: string[]` on ConceptMeta (engine + contracts schemas + upsert inputs incl. MCP/REST/CLI). `get_context` bundles append a `Code areas:` line to each section that has them — that's the payoff: a subagent briefed by get_context knows both the rules AND where to apply them. UIs show them as monospace chips in the concept panel.
- **Vault state**: `onboarded_at` (nullable) on the vault (D1 control-plane column) and mirrored in VaultDO meta; exposed in `vault_stats` / stats endpoints as `onboarded: boolean`.
- **MCP tool `onboard`** (authenticated surface, 9th tool; also in MCP_TOOLS for the local stdio server with core storing onboarded state in vault config):
  - `{action: "start", productName?, repoHint?}` → returns the PLAYBOOK (markdown): instructions to fan out subagents over the codebase (exclude node_modules/dist/.git/lockfiles/binaries), inventory every app file, and distill NOT file-by-file notes but product knowledge structured by the ontology: identify the domains first, then per domain the features (`part_of`), stories mapping to the features that realize them (`realized_by`), specs stating the rules that `govern` them, workflows, decisions, constraints, glossary — every concept carrying `code_areas` pointing at the rough parts of the codebase it lives in; each as `upsert_concept` calls with wiki-links/relations; target 20–60 concepts for a mid-size product; finish by calling `{action:"complete", summary}`.
  - `{action: "complete", summary}` → sets onboarded, stores summary as a `spec`-type concept `product-onboarding-summary`.
  - `{action: "status"}` → {onboarded, conceptCount, byType}.
- **Nudge, not a wall**: while un-onboarded, `get_context` and `search_concepts` responses are prefixed with a one-line notice ("vault not onboarded — call onboard to index your product first"). No hard blocking. Directory surfaces (OAuth and public-vault connections) get the neutral wording instead (`ONBOARDING_NOTICE`: "this vault has not been onboarded yet, so results may be sparse"); see "Directory policy".
- **CLI**: `brainz onboard [--status|--complete]` — same playbook/semantics for local vaults (state in brainz.config.json).
- Docs: dashboard MCP snippets mention onboarding as step 1; marketing /docs gets a subsection.

### Tasks & drift sync (the work loop)

Brownmatter is not just a map of the product — it's the pile of work on it, and it must stay true to the artifact (the codebase). Two capabilities:

**Tasks — "take a task off the pile" (Wave T — build & deploy FIRST, before working any backlog):**
- New concept type `task` (11th) — added to ConceptType in engine + contracts (`conceptTypeSchema`, `CONCEPT_TYPES`) + core + VaultDO + both MCP servers + CLI + both graph UI palettes + docs, exactly as the earlier 4 types were added. A task is a unit of work not yet reflected in the artifact.
- Task frontmatter fields (additive to ConceptMeta, all optional): `taskStatus: "open" | "taken" | "done"` (distinct from concept `status`; default `open` for `task`-type concepts), `takenBy?: string` (free-form agent/orchestrator label), `takenAt?: string` (ISO), `doneAt?: string`. Threaded through engine parse/serialize (`task_status`/`taken_by`/`taken_at`/`done_at` frontmatter), contracts schemas (bump CONTRACTS_VERSION), core, VaultDO SQLite columns (gated additive migration), REST, MCP upsert input, CLI. Relations: a task `realizes` stories/features, `governed_by` specs, `part_of` a domain; `code_areas` say where the work lands.
- MCP tools (authenticated surface — added to MCP_TOOLS registry, both servers iterate): `list_tasks {taskStatus?, domain?}` → tasks with their status/taken fields, oldest-first; `take_task {id?}` → claims a specific task or THE NEXT open one (deterministic: oldest `open` by createdAt then id), sets taskStatus=taken + takenBy + takenAt ATOMICALLY (DO storage is single-threaded so read-modify-write is safe; reject if already taken), and returns the task PLUS an auto-assembled `get_context`-grade bundle for its `part_of` domain + related concepts (code areas included) so the caller can fan out immediately; `complete_task {id, outcome}` → sets taskStatus=done + doneAt, appends `outcome` to the task body, and the result REMINDS the caller to index what changed via upsert_concept so the graph stays true to the artifact (`TASK_COMPLETE_REMINDER`; directory surfaces get the neutral `TASK_COMPLETE_NOTICE`, see "Directory policy").
- The orchestrator contract (in take_task's description + playbook): after implementing, verify the artifact matches every spec that `governs` the task; discrepancies → fix or file a new task; then index the new/changed knowledge.
- `create_task {title, body, domain?, realizes?, governedBy?, codeAreas?}` convenience tool (or via upsert_concept with type task) so findings become first-class tasks. The five current concept-tagged tickets (`task-*`, tag `task-open`) MIGRATE to real `task`-type concepts with `taskStatus:"open"` as part of this wave.

**Real-time Kanban board (part of Wave T):**
- New app route `/v/[slug]/board` (linked from the vault workspace + dashboard): a Kanban with columns **Open · Taken · Done** driven by the vault's `task`-type concepts.
- **Grouping (switchable)**: by status (default columns), by **related concept** (swimlanes per `part_of` domain / the concept a task `realizes`), by priority tag, or by `takenBy`. A group-by control in the board header re-lays out lanes/columns live.
- **Cards** show title, priority/area tags, `takenBy` when taken, and the code_areas count; clicking a card opens the existing concept panel (rendered markdown + edges) so the board and graph share one detail view. Cards link to the concepts the task `realizes`/`is governed_by` (click-through to the graph neighborhood).
- **Real-time**: the board reflects task changes without a manual refresh. Implement via short-interval polling of `GET /v/:id/tasks` (e.g. 3–5s) with diff-and-animate, OR SSE from the Worker if trivial — polling is the acceptable default (VaultDO has no push). Moving a card between columns issues the corresponding `take_task`/`complete_task`/reopen mutation (session-auth) and optimistically updates. An agent taking a task over MCP shows up on the board within one poll — the human watches the fleet work.
- REST: `GET /api/vaults/:id/tasks {taskStatus?,domain?,groupBy?}`, and card moves reuse task mutations. Dashboard vault cards get an open-task count chip; stats expose `openTasks`. Obsidian-dark styling; `task` nodes get their own palette color + open/taken/done badge in the graph view too.

**Drift sync — keep brownmatter true to the artifact:**
- `sync` MCP tool (+ `brainz sync` CLI): `{action: "start"}` → returns a SYNC PLAYBOOK: the vault's `last_synced_at` (+ onboarded state), all concepts' code_areas as a coverage map, and instructions: diff the codebase since last sync (git log/status since timestamp), fan out subagents over changed areas, update stale concepts, index un-mapped new work (features/stories/specs/tasks for incomplete work found), report coverage gaps (code areas no concept references). `{action: "complete", summary}` → sets `last_synced_at`, stores summary in the `product-onboarding-summary` concept (append log).
- Staleness nudge: `get_context` prefixes a one-liner when last_synced_at is older than 14 days ("knowledge may be stale — run sync"), same style as the onboarding nudge, and likewise neutral on directory surfaces (`SYNC_STALENESS_NOTICE`, which states the age without naming `sync`).
- Stats expose `openTasks`, `lastSyncedAt` (UI: task count chip on dashboard cards; tasks filterable in the workspace, `task` gets its own palette color + open/taken/done badge).

### Session defaults — agents use Brainz every session (`session_hook` tool + server instructions)

**Problem:** connecting the MCP server gives an agent the tools but no reason to reach for them; a fresh session only uses Brainz if a human says so. Fix, in two layers, both rendered from `packages/engine/src/session.ts` (one voice, like the onboarding playbook):

- **Server `instructions`:** the local stdio server returns `sessionInstructions()` as the MCP `instructions` on initialize — a short directive primer: `get_context` before planning or delegating, `list_tasks`/`take_task`/`complete_task` for work, `upsert_concept`/`create_task` to write back, `onboard`/`sync` when nudged. **Brainz Cloud sends the neutral `serverInstructions()` instead** on every `/mcp` and `/mcp/agent` vault connection and on the unauthenticated `/mcp` listing: what the vault holds and which tool does what, with no advice on when or how often to use it (directory policy, below). A viewer-scoped connection gets the read-only variant of either (no write/task tools named, since they aren't registered). The unauthenticated `/mcp/agent` signup server sends no instructions.
- **MCP tool `session_hook`** (in MCP_TOOLS, so the local stdio server and cloud `bz_` key connections; NOT in the public read set, and NOT on the cloud directory surfaces — OAuth connections and the unauthenticated `/mcp` listing — per `DIRECTORY_HIDDEN_TOOL_NAMES`): `{client?: "claude-code" | "other", serverName?}` → ONE markdown text block, the SESSION-HOOK PLAYBOOK (same convention as `onboard`/`sync` start; no JSON form). Brainz can't write to the caller's repo, so the playbook instructs the CALLING agent to install the primer in its own harness:
  - **Claude Code:** write the primer to `.claude/brainz-session.md` and merge a `SessionStart` hook (`cat .claude/brainz-session.md`, no matcher → fires on startup, resume, clear, and compact) into `.claude/settings.json`, preserving existing keys and hooks.
  - **Other clients:** add the primer to `AGENTS.md` (or the client's rules file) between `<!-- brainz:session:start -->` / `<!-- brainz:session:end -->` markers.
  - Idempotent: re-running replaces the primer / marked block, never duplicates. Stateless on the Brainz side — nothing is recorded in the vault.

### Dreaming — autonomous nightly vault consolidation (`dream` tool + DO alarm)

**Problem:** the graph only improves when an agent remembers to `sync`. Duplicates pile up, knowledge that only lives in a finished task's `## Outcome` never becomes a concept, and contradictions sit unnoticed. Dreaming is **fully autonomous** background consolidation (user decision 2026-10-27): the server does the thinking and applies the changes itself, no agent in the loop — bounded by hard safety rails and fully revertible. Ideas (not code) from OpenClaw's memory-core dreaming: light → REM → deep phases plus a Dream Diary.

**Where the logic lives.** Everything deterministic is pure engine code in `packages/engine/src/dream.ts` (Workers-safe): candidate detection, the REM prompt + response parser, threshold gates, the loss rail, plan building (the exact after-state of every touched concept), the resumable sweep state machine, and diary rendering. Hosts (VaultDO in cloud, `Vault` in core) only snapshot their data, call the LLM through a provider seam, persist checkpoints, apply the plan and keep preimages.

**A sweep** (one "dream") runs three phases in order over the vault's concepts (`task`-type concepts are inputs, never merge candidates; the `product-onboarding-summary` concept is never touched):

- **Light** (no durable write) — stages what changed since the previous sweep (`updatedAt > lastDreamAt`; everything on the first sweep):
  - *duplicate candidates*: pairs of non-task concepts, at least one of them changed, scored by embedding cosine when both have vectors (`≥ 0.92`), else lexical similarity (same `slugify(title)` ⇒ 1.0, else Jaccard over title+body word tokens `≥ 0.8`). Work is chunked: each step compares at most `lightBatch` (200) changed concepts against the vault.
  - *outcome candidates*: `done` tasks with a `## Outcome` section, done since the previous sweep, that no concept is yet `derived_from`.
  - *hygiene counts*: orphans (no edges either way), pending wiki-links (targets with no concept), concepts lacking `codeAreas`. Counted for the diary only.
- **REM** (no durable write) — an LLM pass over the staged material in chunks (≤ 6 duplicate pairs + ≤ 4 outcomes + changed concept titles per call, at most `maxLlmCallsPerStep` (3) calls per step). The model returns JSON *proposals*, never prose to splice in: `merges [{keep, drop, confidence}]`, `promotions [{task, title, type, body, confidence}]`, `links [{from, to, relation, confidence}]`, `contradictions [{ids, summary, confidence}]`, `themes [string]`. Malformed output is dropped (counted as `unparseable`), never retried in a loop.
- **Deep** (the only durable write) — gates every proposal, builds the plan, checks the loss rail, applies:
  - *merge* — only for a pair Light staged (the model cannot invent merges), confidence `≥ 0.8`. Survivor `keep` absorbs the other: tags / codeAreas / relations unioned, `drop`'s body appended under `## Merged from <title> (<id>)` unless already contained. Every concept that referenced `drop` (relation targets or `[[drop]]` / `[[drop|label]]` wiki-links) is rewritten to point at `keep` — edges redirect. `drop` is **tombstoned**: removed from the live graph, its full prior state kept in the dream's preimage log.
  - *promote* — outcome of a staged task, confidence `≥ 0.7`, type in `feature | decision | constraint | spec | pattern | glossary | concept`, id (`slugify(title)`) not already taken. Creates the concept with `relations.derived_from: [task]`, tag `dreamed`, and a provenance line.
  - *link* — both ends exist, not already linked with that relation, confidence `≥ 0.7`; appended to the source concept's relations.
  - *contradiction* — confidence `≥ 0.6` ⇒ files an open `task` (`tags: [dream, contradiction]`, `related_to` both concepts) for a human/agent. Dreaming never silently picks a side.
  - Per-sweep caps: `maxMerges` 5, `maxPromotions` 5, `maxLinks` 10, `maxContradictions` 3. Over-cap proposals are rejected with reason `cap`.
  - **Loss rail**: `touched` = existing concepts the plan would remove or modify. If `touched > max(minTouchAllowance (3), floor(maxTouchFraction (0.2) × priorConceptCount))` the WHOLE deep phase is rejected (`rejected: loss-threshold`) and nothing is written. Additions (new concepts, new tasks) don't count.
  - Rejections are reported as counts by reason (`below-threshold`, `not-staged`, `exists`, `missing`, `bad-type`, `cap`, `protected`, `phase-off`, `unparseable`), never by dumping snippets.

**No LLM ⇒ light only.** If no provider is available (no `AI` binding — e.g. `wrangler.dev.jsonc`, tests, local without a provider), REM and deep are `skipped` with a reason and the sweep still writes a diary entry. Same spirit as the embeddings fallback: never crash, always leave a visible trace. LLM failures mid-REM mark REM `skipped` (`llm-error`) and skip deep.

**LLM provider seam** — `DreamLlm { name; complete({system, user, maxTokens}) → Promise<string> }`. Cloud default: Workers AI `@cf/meta/llama-3.3-70b-instruct-fp8-fast` via `env.AI` (no key to manage); a user's own key (BYOK, below) swaps in an Anthropic or OpenAI-compatible provider without touching the engine. Local (`@brainz/core`): `Vault.dream({llm})` takes an injected provider; the CLI ships none yet, so `brainz dream run` locally does light + diary.

**Spend controls (cloud; user decision 2026-10-28 — required before Dreaming is deployed).** REM is the only part of a dream that costs money. Three controls decide, before EVERY REM step, which provider (if any) the step may use. The decision lives in `apps/cloud/src/lib/server/dream-budget.ts` (pure helpers over a D1 handle); the VaultDO reads the D1 control plane through its own `DB` binding.

- **Account = the Brainz user who owns the vault** (`vault.owner_id`). The VaultDO learns its vault id from the `x-brainz-vault-id` header every Worker → DO call carries (stored in DO meta `vault_id`; `ctx.id.name` as a fallback) and resolves the owner in D1. Unknown owner or no `DB` binding ⇒ no operator-paid REM (fail closed).
- **Selection order** (first match wins): (1) kill switch `all` ⇒ REM skipped, reason `disabled: …`; (2) the owner has a stored key ⇒ REM runs on it (`byok:anthropic` | `byok:openai`), outside the cap; (3) kill switch `workers-ai` ⇒ skipped, `disabled: …`; (4) no `AI` binding ⇒ skipped, `no LLM provider available`; (5) the owner's spend today ≥ cap ⇒ skipped, `budget: …`; (6) Workers AI, metered.
- **Daily cap per account.** Default `DREAM_DAILY_USD_PER_ACCOUNT = 1` (USD, a wrangler `var`, raise it without code changes). It covers all of the owner's vaults combined, per UTC day. Each Workers AI dream call is metered in USD from the `usage` the binding returns (`prompt_tokens` / `completion_tokens`), falling back to a chars/4 estimate of prompt and completion, priced with `DREAM_LLM_PRICE_USD_PER_M` (the published Workers AI price for the model, input/output per M tokens, beside `DREAM_LLM_MODEL`). The DO checks the remaining budget before each REM step and adds the step's spend to the ledger after it, so a step can overshoot the cap by at most one step (≤ `maxLlmCallsPerStep` calls). BYOK calls are never metered.
- **Global kill switch.** D1 `control_flag` row `dreaming_kill_switch` (`off` | `workers-ai` | `all`; flipped with `wrangler d1 execute`, no redeploy — exact command in apps/cloud/README.md), overridable by the wrangler var `DREAMING_AI_DISABLED` (`1`/`true`/`workers-ai` or `all`). The stronger of the two wins. `workers-ai` stops every operator-paid call (BYOK users keep dreaming on their own key); `all` stops every dream LLM call. Light still runs either way.
- **Bring your own key.** A user stores ONE dream LLM key on their account: `anthropic` (API key, optional model, default `claude-opus-5-5` at `effort: "low"`) or `openai` (any OpenAI-compatible endpoint: https base URL + key + model, `POST {baseUrl}/chat/completions`). Encrypted at rest in D1 with AES-GCM (256-bit key = SHA-256 of the `BYOK_ENCRYPTION_KEY` secret, random 12-byte IV, the user id as additional data). The plaintext is never returned after saving — only a hint (first 7 characters + `…` + last 4). A key that is invalid, fails, or can't be decrypted makes REM `llm-error` — dreams NEVER fall back to Workers AI.
- **Skipped REM keeps its material.** When REM is skipped for `budget` or `disabled`, the sweep still finishes light-only with a diary entry naming the reason, and the vault remembers the sweep's `since` (DO meta `dream_backlog_since`), so the next sweep (the next day's alarm) re-stages the same material and retries REM. The backlog clears once a sweep's REM runs. Never fails the sweep.

**Per-vault settings (user request 2026-10-30: "dreaming should be configurable").** Every knob is per vault, optional, and defaults to the behaviour above. One shape, `DreamSettings` (engine `normalizeDreamSettings` clamps every field to its bounds; contracts `dreamSettingsSchema` / `dreamSettingsPatchSchema` validate the wire):

| Field | Default | Bounds / values | Effect |
|---|---|---|---|
| `enabled` | `true` | boolean | nightly sweeps on/off |
| `cadenceHours` | `24` | int 1–168 | hours between sweeps |
| `runHourUtc` | `null` | int 0–23 or `null` | preferred UTC hour: when the cadence is ≥ 24h, the next due time is pushed forward to the first `HH:00Z` at/after it (off-peak runs); ignored below 24h |
| `mode` | `"apply"` | `apply` · `propose` · `light-only` | `apply` = today; `propose` = REM + gates run, nothing is written — the gated changes are stored on the diary entry as numbered proposals until approved; `light-only` = no LLM call at all (REM skipped `light-only mode`, never owed as backlog) |
| `phases` | all `true` | `{merges, promotions, links, contradictions}` booleans | a phase that is off is not asked of the model and its proposals are rejected `phase-off` |
| `thresholds` | `{merge 0.8, promote 0.7, link 0.7, contradiction 0.6}` | each 0.5–1 | confidence gates |
| `caps` | `{maxMerges 5, maxPromotions 5, maxLinks 10, maxContradictions 3}` | 1–20 · 1–20 · 1–50 · 1–10 | per-sweep caps (`cap` rejections) |
| `lossRail` | `{maxTouchFraction 0.2, minTouchAllowance 3}` | 0.01–0.2 · 0–3 | the loss rail can only be made **stricter**: values above the default are clamped down, so max(3, 20%) stays the hard ceiling |
| `llm` | `{provider "auto", model null}` | provider `auto` · `workers-ai` · `byok`; model 1–200 chars `[A-Za-z0-9._:/@-]` or `null` | cloud only (local has no built-in provider and only stores it). `auto` = the selection order above; `workers-ai` skips the owner's key (kill switch + cap still apply); `byok` uses only the owner's key — no key ⇒ REM skipped `no LLM provider available: …`, never Workers AI. `model` overrides the BYOK key's model for this vault; the Workers AI model is fixed by the operator |

Out-of-range values are rejected by the wire schema (MCP/REST/CLI) and clamped again by the host, so stored settings are always in bounds. A patch merges into the stored settings (nested objects field by field); `null` clears `runHourUtc` / `llm.model`.

**Propose mode & approval.** A `propose` sweep runs light + REM + the deep gates and the loss rail exactly as `apply` would, then writes nothing: the diary entry gets `status: "proposed"`, `deep.status: "proposed"`, and `proposals: [{n, kind, id, summary, decision: "pending"}]` (the gated changes, numbered from 0); the host keeps the sweep state with only the accepted REM proposals. `dream {action: "apply", id, proposals?}` approves `proposals` (the `n`s; omitted = all) and rejects the rest: the selected proposals are re-gated and re-planned against the CURRENT vault (a proposal whose target has since gone or been taken is rejected `missing`/`exists`; the loss rail is re-checked), applied with preimages like any dream (so it can be reverted), and the entry becomes `applied` / `nothing-applied` / `rejected` with each proposal's `decision` set and `decidedAt`. `proposals: []` rejects them all ⇒ `status: "dismissed"`. Applying a non-pending entry is an error. A proposal approved later is still bounded by the caps and the rail.

**Preimages & revert.** Before applying, the host records a preimage per touched concept (cloud: the full DO row; local: the raw markdown file + path; `null` for created concepts) and the after-state's `updatedAt`. `dream {action:"revert", id}` restores every preimage (deletes created concepts, restores modified/tombstoned ones byte-for-byte, rebuilding edges/FTS) — the vault returns to its exact pre-dream state. Revert **refuses** (listing conflicts) when any touched concept changed after the dream (its current `updatedAt` ≠ recorded after-state or it was deleted/created since), so later agent work is never clobbered. A dream can be reverted once; the diary entry is marked `reverted`.

**Dream Diary.** One entry per sweep that found material: `{id, startedAt, finishedAt, trigger: "alarm"|"manual", status: "applied"|"nothing-applied"|"rejected"|"light-only"|"reverted"|"proposed"|"dismissed", mode?, phases: {light, rem, deep}, applied: [{kind, id, summary}], proposals?: [{n, kind, id, summary, decision}], decidedAt?, rejected: {reason: count}, themes, markdown}`. Counts and ids, not dumps. An empty sweep (nothing changed since the last one) records `lastDreamAt` and writes no entry.

**Storage.**
- Cloud (VaultDO, schema v7, additive; v8 adds `dream.pending_json` — the stored sweep state of a `proposed` entry, cleared once decided): table `dream(id TEXT PK, started_at, finished_at, trigger, status, diary_json, preimage_json, reverted_at, pending_json)`; meta keys `dream_enabled` (default on), `dream_cadence_hours` (default 24, 1–168), `dream_settings` (JSON of the other per-vault settings; absent ⇒ defaults), `last_dream_at`, `dream_checkpoint` (JSON sweep state while a sweep is in flight), `vault_id` (the DO's vault, for spend attribution), `dream_backlog_since` (set while REM is owed after a `budget`/`disabled` skip; `*` = since the beginning).
- Cloud (D1 control plane): `dream_spend(user_id, day, usd_micros, calls, updated_at)` PK `(user_id, day)` — the per-account daily ledger (`day` = UTC `YYYY-MM-DD`, integer micro-dollars); `llm_key(user_id PK, provider, ciphertext, iv, key_hint, base_url, model, created_at, updated_at)` — one BYOK key per user, AES-GCM ciphertext; `control_flag(key PK, value, updated_at)` — operator flags (`dreaming_kill_switch`). Diary retention: newest 50 entries (older rows pruned with their preimages).
- Local: `<vault>/.dreams/<id>.json` (diary + preimages, plus `pending` sweep state while `proposed`), `lastDreamAt` and the per-vault settings (`dreaming: {enabled, cadenceHours, runHourUtc, mode, phases, thresholds, caps, lossRail, llm}`) in `brainz.config.json`. NOT under `.brainz/` — preimages are not derivable state.

**Scheduling (cloud).** The VaultDO schedules its own DO alarm: on construction, if dreaming is enabled and no alarm is set, it sets one `cadence` hours after the last dream (or from now), moved to the preferred `runHourUtc` when set (see Per-vault settings). `alarm()` advances the in-flight sweep by ONE bounded step (`lightBatch` comparisons, ≤ `maxLlmCallsPerStep` LLM calls; deep applies in one step since touched is bounded by the rail) and persists the checkpoint; if the sweep isn't finished it re-arms the alarm for +1s, else for the next cadence. That keeps every invocation inside the Workers CPU-time and subrequest budget. Embeddings for concepts a dream writes are recomputed (≤ the touched bound). `destroy` deletes the alarm. Disabling dreaming clears the alarm and any in-flight checkpoint.

### Onboarding at scale — coverage-driven continue/status loop (Wave O-scale)

**Problem:** the onboarding playbook says "target 20–60 concepts," so agents stop at ~40 even on a 500+ concept codebase — they obey a flat cap that's wrong for large repos. Fix: make onboarding size-aware, resumable, and coverage-gated so it indexes the WHOLE project.

- **No flat cap.** The playbook stops prescribing 20–60. Instead it tells the agent to size the effort from the codebase (list packages/apps/major dirs; budget concepts per area; large repos → hundreds of concepts) and index **each area to saturation** before moving on. Depth guidance is per-area, not global.
- **`onboard {action:"status"}` becomes a COVERAGE REPORT** (not just counts): given the vault's concepts' `code_areas`, compute which top-level source areas (packages/*, apps/*/src subtrees, major dirs) are UNCOVERED (no concept references any file under them) vs covered, plus conceptCount and byType. The agent calls status to see what's left. Optionally accept `{codeAreasSeen?: string[]}` so the agent can report the areas it has surveyed and status diffs against the real tree (agent supplies the file list from its own repo walk, since the DO can't read the repo).
- **The continue loop (documented in the playbook):** survey → for each area: index to saturation via upsert_concept → call `onboard {action:"status"}` → if uncovered areas remain, keep going (take the next area) → repeat until coverage is broad. This is the agent's loop; Brainz provides the coverage signal each iteration so a fan-out agent doesn't stop early.
- **`onboard {action:"complete"}` is coverage-gated:** reject completion (isError with the list of uncovered areas) when coverage is thin — i.e. a large fraction of the reported source areas have zero concepts. The caller must pass the repo's area list (or a coverage summary) so complete can judge; if it can't judge (no area list supplied) it warns rather than hard-blocks. On success it still stores the summary + quality signals (conceptCount, lacking-codeAreas count, domain presence, byType) added earlier.
- **Playbook + tool descriptions** teach: "for a large project expect 200–800+ concepts; do NOT stop at a few dozen; loop status→index until coverage is broad; only then complete." Engine change is `onboard.ts` (playbook text + a pure `computeCoverage(concepts, areaList)` helper); cloud/local handlers thread it through `mcp.ts` / the stdio server + contracts (status/complete output schemas gain `coverage`, bump CONTRACTS_VERSION). This coverage machinery is REUSED by the `sync` epic (drift = areas whose code changed since last sync).

### Agent self-signup guardrails: anonymous signup + claim-to-persist + self-onboard skill (Wave G)

Threat model this wave closes (from the July 2026 review): (1) `signup` required an email and immediately created a PERMANENT account + key with no human approval ever; (2) the returned `loginUrl` was a session-granting URL handed into agent context/logs — the agent could open it itself, minting a session and laundering `emailVerified: true` without any inbox proof; (3) email squatting — an agent could register any unowned address, whose real owner would later magic-link in and silently inherit a vault with an attacker-held API key; (4) signup's "already exists" error was an account-enumeration oracle. The fix inverts the model: **anonymous ephemeral signup; persistence requires the inbox owner to approve an EMAILED link.**

**Signup v2 (public MCP `signup`)** — see the amended "Agent-driven signup" section above. Summary: `{vaultName?, email?}` → provisional account (placeholder email `unclaimed-<userId>@pending.brainz.invalid`, `expires_at = now + 7d` — new nullable `expires_at` D1 column on `user`), vault, API key; output `{apiKey, vaultSlug, expiresAt, claimEmailSent}` (strict; CONTRACTS_VERSION bump); never any URL. Supplying `email` just auto-fires a claim request.

**`claim` tool (authenticated MCP surface — cloud-only, NOT in `MCP_TOOLS`)**:

- Contract lives in `@brainz/contracts` as a cloud-only registry (e.g. `CLOUD_MCP_TOOLS`) registered ONLY by apps/cloud's authenticated server alongside the vault tools; the local stdio server never sees it.
- Input `{email}` (validated format). Resolves the calling key → vault → owner. Already-claimed owner (`expires_at` null / non-placeholder email) → isError "already claimed — manage keys in settings".
- Mints a **claim token**: 32 random bytes, SHA-256 hash at rest in new `account_claims` table `(id, user_id, email, token_hash unique, created_at, expires_at +24h, approved_at nullable)`. A new request supersedes (deletes) the user's prior pending claims.
- Delivery is **EMAIL ONLY** via the Mailer (`sendClaimApproval({to, url, vaultName, keyName, keyPrefix})`, branded template: "An agent set up a Brainz workspace and wants to attach it to your email — review and approve"). The URL (`/claim/<token>`) is NEVER present in the tool result. If the address already has an account, send a notice email instead (no token: "an agent tried to attach a workspace to your address — you already have an account; sign in to review"). Tool output is identical either way: `{status: "sent", expiresAt}` — no enumeration oracle.
- Rate limits: claim requests are counted in `magic_link_events` under the existing guard limits (5/hour/email, 20/hour/IP) — same abuse surface (unsolicited email to arbitrary addresses).

**`/claim/[token]` approval page (revived route)**:

- Load: SHA-256 the token, fetch unexpired unapproved claim; show what's being approved — the email being bound, vault name, API key name + `keyPrefix`, workspace created date, and copy stating an agent will retain access via that key. Invalid/expired/used → clear error page with "ask your agent to request a new claim" guidance.
- **Approve** (form action, atomic): re-validate; set `user.email = claim.email`, `emailVerified = true`, clear `user.expires_at`, fix placeholder `name`; stamp `approved_at`; delete the user's other pending claims; sign the human in (server-side session mint — e.g. an internally-minted magic-link verify redirect served ONLY to this browser; implementation is agent's call) and land on /dashboard. Single-use: a consumed token never approves twice.
- **Decline** (form action): delete the pending claim; the workspace simply expires on schedule. Copy tells the human nothing else is needed and nothing was attached to their email.
- Approval is the ONLY path that flips a provisional account permanent; the session-create `emailVerified` hook (Wave A hardening) stays as-is.

**Expiry enforcement**: `resolveApiKey` (the single bearer-auth chokepoint for REST + MCP) loads the key's vault owner and rejects when `expires_at < now` (401, "workspace expired unclaimed — sign up again, or ask your human to approve the claim email"). Hard deletion/purge of expired rows + DO storage is deferred (expired accounts are inert); an admin purge script may come later.

**Self-onboard skill (user-facing deliverable)**: a single copy-paste markdown doc a user drops into their agent of choice (Claude Code, Cursor, any MCP client) so the AGENT can set Brainz up end-to-end.

- Canonical file: `apps/cloud/static/skill.md`, served at `https://brainz.brownmatter.ai/skill.md`; plus a `/skill` page in the app UI (marketing-style, session not required) that renders it with a one-click "copy system prompt" button; splash page links to it ("Set up via your agent").
- Content = a SYSTEM PROMPT for the agent covering: what Brainz is (shared product-knowledge graph for agent fleets); connecting over MCP (`claude mcp add --transport http brainz https://brainz.brownmatter.ai/mcp --header "Authorization: Bearer bz_..."` + raw `.mcp.json` equivalent); calling `signup` unauthenticated (keep `apiKey` secret — never log/echo it; note the 7-day unclaimed expiry); persisting via `claim` (ask the human for their email, call `claim`, tell the human to open the approval email — the agent never sees the link); running `onboard` to index the product; the vault toolset (search/get_context/upsert/tasks/sync) and when to use each; security rules (never print keys, never ask the human to forward the approval email).
- The skill text must match the shipped contracts exactly (tool names, input shapes, expiry windows) — treat drift as a bug.

**Verification (Wave G)**: unit tests for signup v2 (anonymous + with-email), claim request (eligible / already-claimed / already-registered / rate-limited), approval action (happy, expired, reuse, decline), expiry enforcement at `resolveApiKey`; e2e: signup → key works → claim → DevMailer captures approval URL → approve → human session on /dashboard → key still works and account is permanent; and signup → never claim → clock past expiry → key 401s.

### OAuth 2.1 for remote MCP (Wave OA — directory listing)

The Claude Connectors Directory and the ChatGPT plugin directory both require OAuth for an MCP server whose tools act on a user's account: Anthropic accepts a static key only as an org-Owner beta, and OpenAI has no API-key or fixed-header input at all. Brainz therefore runs its own OAuth 2.1 authorization server (AS) on the Worker origin, and `/mcp` accepts its access tokens alongside `bz_` keys. Requirements are from https://claude.com/docs/connectors/building/authentication, `/lazy-authentication`, the MCP authorization spec (2025-11-25), and https://developers.openai.com/plugins/deploy/submission.

**Hand-rolled, not Better Auth's `mcp`/`oidcProvider` plugin.** That plugin (deprecated in favour of `@better-auth/oauth-provider`) stores tokens in plaintext, never invalidates a used refresh token, only issues refresh tokens for `offline_access`, has no client-ID-metadata-document support and no way to bind a grant to a vault. The AS lives in `$lib/server/oauth.ts` (logic over a small `D1Like` port, unit-tested on the migrated schema) and the routes below. Better Auth stays the identity layer: the consent page reads the Better Auth session.

**Issuer and discovery.** Issuer = `BETTER_AUTH_URL` (production `https://brainz.brownmatter.ai`), else the request origin. The protected resource is `<issuer>/mcp`.

- `GET /.well-known/oauth-protected-resource/mcp` and `GET /.well-known/oauth-protected-resource` (RFC 9728): `{resource: "<issuer>/mcp", authorization_servers: ["<issuer>"], scopes_supported: ["vault"], bearer_methods_supported: ["header"], resource_name: "Brainz", resource_documentation}`.
- `GET /.well-known/oauth-authorization-server` (RFC 8414): authorize/token/register/revoke endpoints under `/oauth/*`, `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none", "client_secret_post", "client_secret_basic"]`, `scopes_supported: ["vault", "offline_access"]`, `client_id_metadata_document_supported: true`.
- Wire shapes live in `@brainz/contracts` (`oauth.ts`); the routes parse their own output against them.

**Client registration: DCR and CIMD.**

- `POST /oauth/register` (RFC 7591, JSON). `redirect_uris` must be non-empty (max 5, each at most 512 chars; `client_uri`/`logo_uri` at most 512, `client_name` 200, `scope` 200). Each must be `https:` with no fragment, or `http:` on a loopback host (`localhost`, `127.0.0.1`, `[::1]`). Only the `authorization_code` and `refresh_token` grants and the `code` response type are accepted. `token_endpoint_auth_method` is `none` (public client, PKCE only) or `client_secret_post`/`client_secret_basic` (the confidential client gets a `bzcs_` secret, shown once and stored SHA-256-hashed). The response is 201 with `client_id` (`bzc_…`). Registration is unauthenticated, so it is bounded three ways:
  - **Per-bucket limit:** a durable D1 limit (`oauth_register_events`, record-then-count) allows 20 registrations per bucket per hour, else 429.
    - The bucket is the IPv4 address or the **IPv6 /48**, so an attacker can't rotate the 65,536 /64s of one /48 to multiply the limit.
    - The other guards (signup, public reads, magic links, password sign-in) keep `resolveRateLimitIp`'s IPv6 /64 bucketing (`rateLimitBucket`). Those limits are small per-user allowances, and a /48 often covers a whole site or organisation.
  - **Global backstop:** 20,000 registrations per hour across all non-directory traffic. It only bounds table growth; the per-/48 limit does the work, so a few /48s can't lock ChatGPT, Claude Code or Cursor out.
  - **No growth when full:** a request against a bucket that is already full is refused without recording a row.
  - **Directory egress exempt:** Anthropic's `160.79.104.0/21` and OpenAI's published ChatGPT-integrations egress skip both limits, because those directory clients register from shared addresses on every fresh connection.
    - OpenAI's list is <https://openai.com/chatgpt-connectors.json>, documented at <https://developers.openai.com/api/docs/guides/ip-addresses>.
    - It is a committed snapshot, `src/lib/server/openai-egress.ts`, regenerated with `scripts/refresh-openai-egress.mjs`. OpenAI says the ranges change, so refresh it before a submission. A stale entry just falls back to the per-bucket limit.
  - **Small rows:** the field caps above.
  - **Purge:** each registration also purges DCR clients that have no grant and no live code and have been **idle for 30 days**. Idle means no authorize-page use (`oauth_client.last_used_at`, stamped by the consent page load), or no registration if never used. It also purges registration events older than the window. The long TTL matters because native clients such as Claude Code cache their `client_id`, and a client whose only grant was cascade-deleted with its vault must still work when the user returns. The daily housekeeping cron (below) runs the same client purge after dropping dead grants.
- **Housekeeping cron.** A Worker cron trigger (`triggers.crons` in `wrangler.jsonc`, daily at 04:23 UTC) runs `purgeExpiredOAuthState` (`$lib/server/scheduled.ts`; `scripts/patch-worker.mjs` attaches the `scheduled` handler to the adapter's default export, and the build fails if it can't). Every statement is idempotent, so a run that is cut short is finished by the next one. In order, it deletes:
  1. authorization codes more than a day past `expires_at`. A replay within that day still finds the code and revokes its grant;
  2. tokens past `expires_at`, and every token of a revoked grant. Superseded or rotated tokens that have **not** expired stay, because presenting one is reuse and must still revoke the grant;
  3. grants revoked more than 30 days ago, and unrevoked grants older than a day with no token left, which means their last refresh token expired and nothing can use them. Their `oauth_grant_vault` rows and tokens are deleted explicitly, not left to the FK cascade. The one-day margin covers the code exchange, which inserts the grant before its first token pair;
  4. the idle-client purge above. A DCR client therefore outlives its last grant's revocation by at least 30 days, so a cached `client_id` keeps working when the user reconnects soon after.
- Client ID metadata documents: a `client_id` that is an `https://` URL with a path is fetched at authorize time (5 s timeout, JSON content-type required, no redirects, no IP-literal or localhost hosts). The body is **streamed with a byte counter and cancelled past 16 KB**, never buffered whole, because `content-length` may be absent and the fetch happens before any session check. The document's `client_id` must equal the URL, and it is treated as a public client. The consent screen names the URL's host, not the self-asserted `client_name`.
- Redirect matching is exact string equality, except loopback `http:` URIs, which match with the port ignored (RFC 8252 §7.3, and `localhost` too, because Claude Code declares it). This accepts `https://claude.ai/api/mcp/auth_callback` and Claude Code's `http://localhost:<any>/callback`. ChatGPT registers its own callback through DCR, so its exact URL (unconfirmed in OpenAI's docs) needs no allowlist.

**Authorization: `GET /oauth/authorize` (consent page).**

- Requires `response_type=code`, a known `client_id`, a `redirect_uri` that matches (optional only when the client registered exactly one), `code_challenge`, and `code_challenge_method=S256`. `plain` is rejected. `state` is passed through. `scope` is narrowed to `vault`. A `resource` (RFC 8707), if sent, must equal `<issuer>/mcp`, else `invalid_target`.
- **The GET never redirects an error.** Anyone can register a client with their own redirect URI, so bouncing errors from the page load would be an open redirector (RFC 9700 §4.11.2). Any invalid request renders an error page. Errors go back to the client (`error`, `state`, `iss`) only from the consent actions, after the user has signed in and clicked: an invalid re-validated request, or Deny → `access_denied`.
- No session: 303 to `/login?next=<authorize URL>`. Every login method returns there (magic link `callbackURL`, GitHub, password).
- The consent screen shows the client (registered name, or the CIMD host), the redirect host (with a warning when it is loopback-only), what is granted ("search, read and write the concepts and tasks in the vaults you pick, read only where you're a viewer"), and a **vault picker**: a checkbox per member vault with the user's role (the first starts ticked), plus **"All my vaults, including ones I create or join later"**. The granted-scope line follows the choice ("the vaults you pick", or "all your vaults, including ones you create or join later"). While "all" is ticked the individual vaults are disabled and the page says so.
  - **CIMD client with a loopback redirect:** this is a program on the user's computer, not the website that publishes the document. Claude Code connects with claude.ai's client-ID metadata document and `http://localhost:<port>/callback`, so naming it "claude.ai" would be wrong. The heading is "Connect an app on your computer to Brainz", the intro names the document's host as the publisher of its public client ID (for claude.ai: "which is how Claude Code connects"), and the warning says any program on the computer can use a public client ID, so approve only a connection the user just started. A CIMD client with an https redirect (claude.ai itself) keeps "Connect claude.ai to Brainz"; a DCR client keeps its self-asserted name and the loopback warning.
  - **More than 5 vaults:** search-and-select over the same checkboxes. A search box filters the rows by name or slug (Enter ticks the first unticked match and never submits; Escape clears), ticked vaults show as removable chips above the list, the list scrolls, and a polite live region says how many match or are selected. "All my vaults" sits above the search and disables it. Progressive enhancement: the search and chips appear only once the page has hydrated; without JS the full checkbox list submits as is. With 5 or fewer vaults it is the plain checkbox list.
  - **Order:** vault picker, then **"+ New vault"** (a styled name input with its own submit), then **Allow access**, then Cancel. Allow is outside the approve form (`form="consent-approve"`) so the new-vault form can sit above it without nesting forms.
  - **Single submit:** the first submit of any of the three forms puts the page in a processing state ("Connecting…" or "Creating…" with a spinner) and disables Allow, Cancel and "+ New vault"; a second submit is dropped. Only buttons and name-less controls are disabled, so the submitted fields are unchanged. A page restored from the back/forward cache leaves the processing state.
  - A **"+ New vault"** form (also the only control when the user has no vault yet) creates a vault without leaving the flow. It is the named form action `?/createVault`, so the `hooks.server.ts` CSRF re-check applies. It uses the same code path as `POST /api/vaults` (`$lib/server/vaults.createVault`): the same slug rules, a 409 on a taken slug, the session user as owner, and the vault and owner membership inserted atomically. It never mints a code. It 303s back to the same authorize URL with `tick=<new id>` plus the earlier ticks, and the re-rendered consent pre-ticks those; the user still has to Approve. Approve or Deny posts back to the page (same-origin form). Approve re-validates everything plus membership on every ticked vault; it needs at least one ticked vault or "all".
- **One grant = one user × one client × a vault set** (see "Multi-vault grants" below). To change the set, the user connects again.
- Approve mints an authorization code (5-minute TTL, single-use, SHA-256 at rest) bound to client, redirect URI, PKCE challenge, user and vault selection, and 303s to `redirect_uri?code=…&state=…&iss=<issuer>`. Deny redirects with `error=access_denied`.
  - **Idempotent per authorize request.** A live test showed a double-clicked Allow minting 2–3 codes; the client exchanged the first (single-vault) one and the two-vault choice was lost. Now there is one code per request: `oauth_code.request_key` (unique) is SHA-256 of (user, client, redirect URI, PKCE challenge, state). The code is `BASE64URL(HMAC-SHA256(BETTER_AUTH_SECRET, "oauth-code:" + code_nonce))` (32 bytes, 43 chars) with the random `code_nonce` stored, so a database read alone cannot rebuild a live code but the server can re-derive it.
  - A duplicate approve while the code is unused and unexpired gets the **same code**, and the row takes the **latest** selection (the last click is what the user sees; the exchange's atomic `used_at` claim orders it against the update). After the client exchanged the code, a duplicate is rejected with 409 "already approved and completed" and **no redirect**, since resending a used code would be a replay that revokes the grant. An expired, never-exchanged code for the same request is replaced by a fresh one. Codes from before migration 0015 have NULL `request_key` and never conflict.

**Tokens: `POST /oauth/token`.**

- Accepts `application/x-www-form-urlencoded` (RFC 6749 §4.1.3; JSON is tolerated). Client authentication: HTTP Basic or `client_secret_post` for confidential clients, `client_id` alone for public ones.
- `authorization_code`: the code must be unexpired and unused, issued to this client, for this exact `redirect_uri`, and `BASE64URL(SHA256(code_verifier)) == code_challenge`. If the authorization request carried `redirect_uri`, the token request **must** repeat it: omitting it gives `invalid_request` and a mismatch gives `invalid_grant`. The code row records `redirect_uri_explicit`. Replaying a used code is `invalid_grant` and revokes the grant it produced. Success creates an `oauth_grant` row and returns `{access_token: "bzat_…", token_type: "Bearer", expires_in: 3600, refresh_token: "bzrt_…", scope: "vault"}` with `Cache-Control: no-store`. A refresh token is always issued; `offline_access` is not required.
- `refresh_token`: refresh tokens **rotate**. A successful refresh marks the old token used and returns a new pair (30-day sliding lifetime).
  - **Token families:** every pair records `parent_hash`, the refresh token it was rotated from, so a refresh token never has more than one live child chain.
  - **Grace window:** the same client presenting a token rotated ≤ 60 s ago is a concurrent refresh or a retry after a lost response. The window is set by `OAUTH_REFRESH_GRACE_SECONDS`, clamped to ≤ 300 s; the E2E uses 3 s.
    - It gets a fresh child pair, and every earlier child of that parent is **superseded** (`oauth_token.revoked_at`). Only hashes are stored, so the earlier pair can't be returned verbatim.
    - This is allowed only while none of those children has itself been rotated, i.e. the chain hasn't moved on.
    - **Every** issuance from a parent (the first-use rotation as well as a grace re-issue) inserts its pair first and then supersedes all its siblings **and their descendants**, in a recursive walk down `parent_hash`. The last insert wins, and the worst case for an interleaving is no live chain (re-authorize), never two.
  - **Reuse = theft:** any of these revokes the whole grant and fails with `invalid_grant`:
    - presenting a superseded sibling;
    - presenting a rotated token outside the window;
    - presenting a rotated token whose child has already rotated.

    A thief replaying a stolen token inside the window can therefore only displace the legitimate chain, and the legitimate client's next refresh revokes the grant. Superseded access tokens stop working immediately. Expired or revoked tokens, a client mismatch, or a grant that no longer covers any vault the user belongs to also fail with `invalid_grant`, never `invalid_request`.
- Errors are RFC 6749 JSON `{error, error_description}`: 400, or 401 for `invalid_client`.
- `POST /oauth/revoke` (RFC 7009) revokes the token's whole grant and always answers 200.
- All tokens and codes are SHA-256 hashed at rest (`oauth_client`, `oauth_code`, `oauth_grant`, `oauth_grant_vault`, `oauth_token` D1 tables). Tables cascade on user and vault delete; a multi-vault grant is re-anchored first (below).
- **Clickjacking.** Every HTML document is sent with `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` (in `hooks.server.ts`), because nothing in the app is meant to be framed, least of all the consent page.
- **CSRF exemption.** SvelteKit's built-in origin check rejects any cross-origin form POST before hooks run, and server-to-server token requests carry no matching `Origin`. `svelte.config.js` therefore sets `csrf.trustedOrigins: ["*"]`, and `hooks.server.ts` re-applies the identical check (`isCrossSiteFormPost`) to every path except `/oauth/token` and `/oauth/revoke`. Both are non-cookie, client-authenticated endpoints.

**`/mcp` with OAuth, and lazy authentication.**

- `Authorization: Bearer bzat_…` resolves token → grant → vault(s). Expired or revoked tokens, a revoked grant, an owner past `expires_at`, or a user who is no longer a member of any covered vault all get 401. On a single-vault grant the user's **current** membership role sets the surface: owner or editor gets the directory vault toolset (`DIRECTORY_MCP_TOOL_NAMES`: every vault tool except `session_hook`), and viewer gets the read tools only (`PUBLIC_VAULT_READ_TOOL_NAMES`, the same server as a public-vault token). A multi-vault grant gets the routed server described in "Multi-vault grants". Every OAuth connection, viewer included, also gets `create_vault` (`OAUTH_MCP_TOOLS`; see "Creating a vault over MCP"). The cloud-only `claim` tool is not registered for OAuth connections, because an OAuth user is already a signed-in human.
- `bz_` keys and public-vault tokens keep working exactly as before.
- **Lazy authentication.** A `/mcp` request with NO Authorization header gets the directory listing server (`buildDirectoryListingMcpServer`): it lists the directory vault tools (`DIRECTORY_MCP_TOOL_NAMES`) followed by `create_vault` (`OAUTH_MCP_TOOLS`), with their annotations, and the neutral instructions, so directory clients know the gated tools exist. It lists no `signup`, `sign_in`, `session_hook` or `claim`, and has no callable tool. Before the MCP SDK runs, the route inspects the JSON-RPC body (single or batch). **Every** `tools/call` gets **HTTP 401** with `WWW-Authenticate: Bearer resource_metadata="<issuer>/.well-known/oauth-protected-resource/mcp", scope="vault"`. Per RFC 6750 §3.1 there is no `error` code, because no credentials were sent. It is never a 200 `isError`, because only a transport-level 401 makes Claude or ChatGPT start sign-in. `initialize` and `tools/list` pass through. Both endpoints share one handler, `$lib/server/mcp-endpoint.ts` (`handleMcpRequest(event, "directory" | "agent")`).
- Every bearer 401 on `/mcp` (invalid, expired or revoked token or key) carries the same `resource_metadata` challenge plus `error="invalid_token"` and an `error_description`, so a client with an expired access token refreshes or re-authorizes.

**Multi-vault grants.** One connection can cover several vaults, so a user with many vaults needs one connector per client, not one per vault.

- **Vault scope.** A grant's `vault_scope` is one of:
  - `single`: one ticked vault. Its `/mcp` surface is exactly the Wave OA one above, with no routing argument.
  - `selected`: two or more ticked vaults.
  - `all`: "All my vaults, including ones I create or join later". It covers every vault the user is a member of at call time, including vaults created or joined after consent.
- **Storage.** `oauth_grant_vault (grant_id, vault_id)` holds the ticked vaults of `single` and `selected` grants; migration 0013 backfills one row per existing grant, all of which are `single`. `all` grants have no rows. The code row carries `vault_scope` plus `vault_ids` (JSON).
- **The anchor.** `oauth_grant.vault_id` is the grant's **anchor**. Since migration 0014 it is nullable with `ON DELETE SET NULL`.
  - 0014 rebuilds `oauth_grant`, because SQLite can't alter a column's NOT NULL or FK. Every other column, the `user_id` FK and the `oauth_grant_user_id` index are unchanged.
  - Dropping the old table cascades into `oauth_token` and `oauth_grant_vault`, even with FK checks deferred. The migration therefore copies both aside and restores them, all in one atomic migration file.
  - A unit test runs it against a populated 0001–0013 schema. Every grant, token, join row and code survives byte-identical, and a failure mid-migration leaves 0013 intact.
  - The deploy runbook (apps/cloud/README.md "Migrations 0013–0014") records the row counts before and after on remote D1.
- **Deploy window.** A `single` grant with **no** join row covers its anchor, still joined against current membership. Grants minted by the old code between `migrations apply` and the deploy have no row, and without this fallback their next refresh would revoke them. An idempotent re-backfill after the deploy makes the rows explicit (README runbook). The fallback can't bring back a vault the user was removed from, because member removal revokes a `single` grant outright (below). The old code's own member removal, in that window, behaves as before multi-vault grants: membership is still checked on every call.
- **Coverage is always intersected with current membership.** Every `/mcp` call and every refresh computes the covered vaults as the join rows (or all memberships for `all`), joined against `vault_member`. Each vault carries the user's current role there. The token exchange keeps only ticked vaults the user still belongs to, and anchors on the first one. If none is left, the token request fails with `invalid_grant`. A `single` or `selected` grant left covering nothing gives 401 on `/mcp`, and its refresh revokes it (`invalid_grant`). An `all` grant with zero vaults stays alive: `/mcp` gives 401 ("this connection covers all your vaults, and you have none yet"), refresh rotates normally, and it works again once the user creates or joins a vault. In a multi-vault grant, vaults whose provisional owner has expired are left out. When every covered vault is such a vault, the token gets the workspace-expired 401.
- **Removing a member drops the vault.** `members.deleteMember` (owner removal or self-leave) runs `oauth.memberRemovalStatements` as **one D1 batch**, a single transaction. It:
  1. revokes the user's `single` grants on that vault, since leaving them with zero rows would read as the deploy-window fallback;
  2. deletes that vault's `oauth_grant_vault` rows from the user's other grants;
  3. deletes the membership.

  Re-adding the user later does not restore a connection's access; they connect again. `all` grants follow membership by definition.
- **Deleting a vault** (`DELETE /api/vaults/:id`) first calls `prepareGrantsForVaultDelete`, one batch that handles the grants anchored on that vault:
  - a `selected` grant moves to another ticked vault, and an `all` grant to another vault the user belongs to;
  - a `single` or `selected` grant with nowhere to go is deleted, and its tokens cascade;
  - an `all` grant with nowhere to go keeps living: the vault delete sets its anchor to NULL.
- **Tool routing (`buildMultiVaultMcpServer`).** `selected` and `all` grants get a routed server:
  - Every vault tool takes the input schema from `MCP_TOOLS` extended with a **required** `vault` argument (`withVaultRoutingArg`, `vaultRoutingArgSchema` in `@brainz/contracts`). Because it is required, a call can never land on a vault by omission.
  - `vault` is a slug or an id. An exact id match wins. Slugs are only unique per owner, so a slug that two connected vaults share is refused with an error asking for the id.
  - `list_vaults` (`MULTI_VAULT_MCP_TOOLS`, read-only annotations) returns `{vaults: [{id, slug, name, role, readOnly}], includesFutureVaults}`.
  - The role is checked on **every call**: a write tool aimed at a viewer vault is an `isError` result naming the vault as read-only. If every covered vault is viewer-only, only the read tools are registered.
  - `session_hook` and `claim` are absent, as on every OAuth connection.
  - Results keep their single-vault contract shapes, and handlers are built only for the vault a call routes to.
  - The server instructions are `serverInstructions({multiVault: true})`, which say neutrally that the connection covers several vaults, that `list_vaults` names them, and that every tool takes `vault`.
- **Unchanged.** `bz_` keys and public-vault tokens stay one vault each. The local stdio server and the unauthenticated `/mcp` listing never show `vault` or `list_vaults`. A directory client re-fetches `tools/list` after OAuth, so it then sees the routed surface. The server card's `_meta` lists `oauthMultiVaultExtraTools: ["list_vaults"]`, ends `oauthTools` with `create_vault`, and lists `agentEndpointApiKeyExtraTools: ["create_vault"]`.
- **Creating a vault over MCP (`create_vault`).** Decided by James on 2026-10-30: "the mcp should be able to make a vault", added to the connection.
  - **OAuth (`/mcp`).** `create_vault {name, slug?}` (`OAUTH_MCP_TOOLS`, annotations `readOnlyHint: false, destructiveHint: false, openWorldHint: false`) is registered on every OAuth connection: single-vault (owner, editor and viewer alike, since the new vault is the user's own) and multi-vault, where it takes no `vault` argument. The vault is owned by the signed-in user and is created by the same `createVault` path as `POST /api/vaults` and the consent page (`$lib/server/vaults`), so the slug rules and limits below are identical.
  - **It joins the connection.** In the same D1 batch as the vault insert (`oauth.grantAddVaultStatements`, each statement guarded on the new vault existing):
    - a `single` grant becomes `selected`, with explicit join rows for its current vault and the new one (so a deploy-window grant with no row also gets both);
    - a `selected` grant gains a join row;
    - an `all` grant already covers it: nothing changes.
    A refused create changes no grant.
  - **Result** (`createVaultOutputSchema`): `{vault: {id, slug, name}, vaults: [{id, slug, name, role, readOnly}], includesFutureVaults, notice}`. `vaults` is what the connection covers after the call, as `list_vaults` would return it. `notice` is one neutral sentence: the vault was added, the connection covers N vaults (and, for `all`, that later vaults are included), every vault tool takes a `vault` argument and `list_vaults` lists them.
  - **The tool surface changes on a single-vault connection.** After the first `create_vault`, the connection has two vaults, so from the next request on it gets the routed server: every vault tool needs `vault`, and `list_vaults` appears. The server is stateless (no session, no standing SSE stream), so it can't push a notification later. Instead, the `create_vault` call that causes the change sends `notifications/tools/list_changed` on its own response stream, before the result (the SDK declares `tools.listChanged`). Clients that honor it re-fetch `tools/list` at once. For a client that keeps its cached list until it reconnects, the result's notice says the connection now covers several vaults and that the `vault` argument appears once the client refreshes its tools. Meanwhile a call without `vault` is rejected by input validation naming the missing argument, and the slugs to pass are in the `create_vault` result. No call ever lands on a vault by omission. `selected` and `all` connections already have the routed surface, so they get no notification.
  - **`bz_` keys on `/mcp/agent`.** `AGENT_KEY_MCP_TOOLS` registers the same tool (same name and shapes; its description names the key) on `/mcp/agent` only. A key is bound to one vault and can't be extended, so the new vault is owned by the key's account (the key's vault owner; keys are owner-minted) and the result also carries `apiKey`, a new `bz_` key for the new vault. It is minted in the same batch, stored as a SHA-256 hash under the name `create_vault (MCP)`, and shown only in that result, like a dashboard-minted key. `vaults` is the calling key's own vault, which the calling key stays bound to.
  - **`bz_` keys on `/mcp`: not offered.** The directory endpoint returns no API keys (directory policy), and the calling key can't reach a vault it didn't come with. A vault the agent can't use, plus an instruction to visit the dashboard for a key, would be a dead end in chat. Agents that create vaults use `/mcp/agent`, and humans use the dashboard or an OAuth connection.
  - **Limits (every create path: REST, consent page, both MCP variants).** An account owns at most `MAX_VAULTS_PER_USER` vaults (wrangler var, default 20) and creates at most `VAULT_CREATE_RATE_LIMIT` per rolling hour (default 10). Both are checked inside the D1 batch that inserts the vault: the vault row is inserted only if the owner is under both limits and the slug is free, and every later statement (membership, grant rows, the agent's key) applies only if that row exists. D1 runs a batch as one transaction, so concurrent creates can't overshoot. The hourly count is the owner's vaults whose `created_at` falls in the last hour, so the limit stores nothing new and `/privacy` is unchanged. A vault deleted within the hour stops counting, but deleting needs the dashboard and only frees a slot under the cap. Errors: slug taken → 409, cap → 403 ("vault limit reached: an account can own at most N vaults; delete one to create another"), hourly limit → 429 ("too many vaults created: at most N per hour; try again later"). Over MCP each is an `isError` result with the same text, and on the consent page it is the inline create error.
  - **Consent copy.** "It will be able to" also says the app can create new vaults for you, which it can then use too.
- **Directory review.** The consent screen states exactly which vaults the app can use, and the "all" option says in words that it includes vaults created or joined later. The `list_vaults` description and the `vault` argument text only describe; they do not steer (the contracts steering lint covers `MULTI_VAULT_MCP_TOOLS`).

**Directory policy (Claude Connectors Directory + ChatGPT directory).** `https://brainz.brownmatter.ai/mcp` is the URL both directories list. The rules below follow the vendors' written policy (reviewed 2026-10-28: https://claude.com/docs/connectors/building/review-criteria, https://developers.openai.com/apps-sdk/app-submission-guidelines) and are guarded by tests:
  - **No API keys in chat.** OpenAI: plugins must not "collect, solicit, or process" "Access credentials and authentication secrets (such as API keys, MFA/OTP codes, or passwords)". `/mcp` therefore never serves `signup` (which returns a `bz_` key in the tool result) or `sign_in`; agent self-signup moved to `/mcp/agent`. Likewise the key-returning `create_vault` variant (`AGENT_KEY_MCP_TOOLS`) is registered on `/mcp/agent` only; the OAuth variant returns no credential. Directory clients authenticate through OAuth only.
  - **Describe, don't steer.** Anthropic rejects tool descriptions that "tell Claude how to behave"; OpenAI rejects descriptions that "recommend overly broad triggering beyond the explicit user intent". Every `MCP_TOOLS` / `CLOUD_MCP_TOOLS` description states what the tool does and returns, with no "THE tool to call", "Step 1", "every session", "do NOT stop" or "before moving on" (a contracts test lints for these). Cloud server instructions are the neutral `serverInstructions()`; the directive `sessionInstructions()` primer stays only on the local stdio server and `brainz hook`, which the user installs.
  - **Neutral notices in results.** Anthropic also rejects tools that "instruct Claude to call external software or tools the user didn't request". On OAuth connections (single- and multi-vault, viewer included) and public-vault tokens, the `notice` on `search_concepts` / `get_context` states the fact without an instruction: `ONBOARDING_NOTICE` and `SYNC_STALENESS_NOTICE` from `@brainz/engine` instead of the directive `ONBOARDING_NUDGE` / `SYNC_STALENESS_NUDGE` ("call the onboard/sync tool with {"action": "start"}"). Likewise the `reminder` on `complete_task` is `TASK_COMPLETE_NOTICE` (the task is done and the rest of the graph is not updated automatically) instead of `TASK_COMPLETE_REMINDER` ("Now index what changed via upsert_concept"). `bz_` key connections and the local stdio server, which the user set up, keep the directive form. The contracts lint test checks the neutral notices too, including that none names a tool. Text returned only because the caller asked for it stays as is: the `onboard`/`sync` start playbooks and the `already onboarded` error on `onboard start` describe how to do what was requested, and the `take_task` briefing is vault content.
  - **No `session_hook` on directory surfaces** (`DIRECTORY_HIDDEN_TOOL_NAMES`). It returns steps for installing a persistent primer in the caller's harness: a hosted chat client has no repo for it, and Anthropic rejects tools that "attempt to override system instructions". `bz_` key connections and the local stdio server keep it.
  - **No upsell.** OpenAI: plugins "must not display subscription plans, initiate new subscriptions, or promote upgrades". No tool description or result mentions plans, pricing or upgrades (Brainz Cloud has no paid tier); the dream spend cap reports its state without suggesting a key or upgrade.
  - **Conversation data.** Anthropic: "Don't collect conversation data beyond what the tool needs" and "Don't query Claude's memory, chat history, conversation summaries, or user files"; OpenAI: no "full conversation history, raw chat transcripts". No tool accepts or requests conversation history. `dream` sends only vault concepts to its LLM (Workers AI, or the vault owner's own Anthropic/OpenAI key), never conversation content; the privacy policy discloses those processors. `session_hook` is stateless and records nothing.
  - **Naming.** The listing, server card and PRM `resource_name` are "Brainz" (OpenAI: "Do not append 'MCP,' 'MCP Server,' or 'Plugin'").

**Reviewer test login (password, operator-provisioned).** Directory reviewers need a login with no email verification step (OpenAI: test credentials must not use "email or other verification schemes"). Magic links fail that rule. Better Auth `emailAndPassword` is enabled with `disableSignUp: true` and `minPasswordLength: 20`. Nobody can create a password account through the app. Only an operator can, with `apps/cloud/scripts/reviewer-account.mjs`, which writes the user and a `credential` account row (Better Auth scrypt hash) into D1 and can seed a demo vault through the REST API.
  - **Reviewer address:** by default (`--directory <name>`) it is unguessable and per directory: `review-<directory>-<12 random chars>@brownmatter.ai`. No inbox is needed.
  - **No guessable addresses:** an address like `reviewer@` would let anyone spend its 5 failures per hour and lock the reviewer out mid-review. An unguessable address also removes the timing signal of which emails have a credential row (scrypt runs only for those). `/login` gets a secondary "Sign in with a password" form for those accounts. The script generates high-entropy passwords.
  - **Gate before Better Auth.** Enabling the provider exposes `POST /api/auth/sign-in/email` to everyone, and Better Auth runs scrypt on every attempt behind a per-isolate limiter. `hooks.server.ts` therefore checks first (`$lib/server/reviewer-login`):
    - **failed-attempt** limits on the durable `magic_link_events` table, in separate `password:`-prefixed buckets so they never touch magic-link quota: 5 failures per email and 20 per IP bucket per hour, else 429.
      - Only failures are recorded: a Better Auth rejection is recorded after it answers, and an allow-list rejection is recorded at the gate. A reviewer who signs in successfully never uses up their allowance.
      - The pre-check counts without recording, so concurrent bursts can overshoot slightly.
    - the allow-list: an email with no `credential` account row gets Better Auth's generic 401 without Better Auth or scrypt ever running.
  - Everyone else stays passwordless.

Threading: a message whose In-Reply-To/References names any known message id (inbound, or a reply we sent) is appended to that task, and a `done` task is reopened. Auto-generated mail (Auto-Submitted, Precedence bulk/list, List-Id, mailer-daemon/no-reply senders) is recorded but only joins an existing thread; it never opens a task.
- **Escalation.** A copy is forwarded (`message.forward`, header `X-Brainz-Support-Category`) to `SUPPORT_ESCALATE_TO` (default james@plutocracy.io, a verified Email Routing destination) for: `reviewer` (From at anthropic.com, openai.com or x.ai or a subdomain, authenticated by DMARC pass or a passing DKIM signature for that domain); `legal` (privacy, GDPR/CCPA, account or data deletion, legal, DMCA/copyright, security wording); `unsure` (no category matched, a reviewer domain that fails authentication, or an unparseable message). `howto`, `bug`, `feedback` and `auto` are left to the agent. The forward happens before storage. If storage fails, or no support vault is configured, the message is forwarded anyway, so nothing is lost. An escalated thread stays tagged `escalated`.
- **Abuse.** Authentication is read from the topmost `Authentication-Results` header (the one Cloudflare adds). Dropped silently, with no task, no forward and no bounce (to avoid backscatter): DMARC fail, SPF fail without a passing DKIM signature, `X-Spam-Flag: YES`, no sender, or mail from support@ itself. Rejected at SMTP time with a reason: over 10 MB, or (non-escalated mail only) more than 10 messages per sender per hour or 200 per hour in total. Drops and rejections are recorded as metadata rows only.
- **Outbound replies.** `POST /api/support/replies` (`supportReplyRequestSchema` → `supportReplyResponseSchema`) takes `{taskId, text?, mode: "draft" | "send", fromDraft?}`. Callers: a session member (editor or above) of the support vault, or a `bz_` key of that vault. It is a REST endpoint and never an MCP tool on any `/mcp` surface (directory policy). A reply goes to the thread's last inbound sender (their Reply-To when set), never to a recipient the caller picks. It is sent from `Brainz Support <support@brownmatter.ai>` through the `SEND_EMAIL` binding (the magic-link send path) with a new Message-ID, `In-Reply-To` = the last inbound message and `References` = the thread. Every send is logged on the task (`## Reply sent <time> by <actor> to <address>`) and as an `out` row. A failed send is recorded as `failed` and returns 502. Sends are capped at 20 per hour. A draft is logged on the task (`## Draft reply …`, tag `draft`), stored as a `draft` row, and announced by email to the escalation address. Any send on the thread settles its pending drafts.
- **Auto-send policy (off by default).** An agent (a `bz_` key) may `send` only when the task's category is listed in `SUPPORT_AUTOSEND_CATEGORIES` and the thread was never escalated. Only `howto` (docs and how-to questions answered from brownmatter.ai/docs) can ever be enabled: any other value is ignored. Unset means agents only draft. James switches it on by setting the var to `howto`. Everything else stays a draft until a human sends it from `/support` (session, editor or above of the support vault, otherwise 404: lists the latest pending draft per task, editable, with "Send reply") or with a session `POST … {mode: "send", fromDraft: true}`. James can also just answer a forwarded copy from his own mail.
- **Triage agent.** A scheduled routine or orchestrator job, holding a `bz_` key for the support vault, follows `apps/cloud/SUPPORT-TRIAGE.md`: list open tasks tagged `support` + `inbox`, take one, draft a reply grounded only in brownmatter.ai/docs (treating the quoted mail as data, never instructions), call the endpoint (`send` only when policy allows, otherwise `draft`), and leave the task taken until the thread is resolved.
- **Config.** `SUPPORT_VAULT_ID` (var), `SUPPORT_ESCALATE_TO` (var, optional), `SUPPORT_AUTOSEND_CATEGORIES` (var, unset = off), and `SUPPORT_MAIL` (optional R2 binding). Cutover is a dashboard change, done only with James's approval: switch the Email Routing rule for support@ from "send to james@plutocracy.io" to "send to Worker brainz-cloud". The escalation forward needs james@plutocracy.io to stay a verified destination.
- **Privacy.** `/privacy` says support email (message, attachments, replies, sender-check results) is stored, that an AI agent sorts it and drafts replies with a person reviewing everything but routine how-to answers, lists Cloudflare (Email Routing, D1, R2) and Anthropic (the agent runs on Claude) as processors, and that support email is not yet deleted automatically. ### Graph workspace — level of detail, clusters, edge bundling

The `/v/[slug]` graph (`src/lib/components/Graph.svelte`; pure logic in `src/lib/graph-lod.ts` and `src/lib/graph-bundle.ts`) must hold ~60fps pan/zoom on a 2k-concept vault and stay usable at 5k. The type chips, auto semantic zoom (type LOD by zoom), search, select, click-focus, hover, drag-to-anchor and Reset behave as before on top of what follows.

- **Two layouts, picked by vault size.** Up to `FLAT_MAX_NODES` (250) concepts: the flat layout, which is one force simulation over the type-filtered nodes, clustered by type. Above that: the clustered layout described below. The choice depends on the vault's concept count, never on the filters, so toggling a chip never swaps layouts.
- **Clusters.** A concept's cluster is the root of its `part_of` chain, followed transitively and cycle-safe: normally a domain. That is how vaults are built (features, stories and specs hang off domains), so clusters match the areas people navigate by and stay stable across edits. A concept with no `part_of` parent and no children falls into a per-type fallback cluster ("Unfiled spec"). A cluster over 400 members is split by type, then into chunks.
- **Clustered layout.** Each cluster gets a footprint disc sized from its members' collision radii. Only the discs are force-simulated (aggregated cluster links attract, discs never overlap). The simulation settles synchronously on load, so there is no animated relayout, and it reheats only while a disc is being dragged. Settled positions are cached per vault in localStorage (`brainz:graph-layout:<vaultId>`); Reset clears that cache. A cluster's members are laid out inside its disc once, on first need, with a short static d3 run over all of its members (every type, so type filters never re-layout), and then cached. Clusters near the viewport are laid out ahead of time when the browser is idle, and each LOD pass spends at most 10ms on new cluster layouts.
- **Level of detail.** The LOD pass is throttled to one run per 100ms during pan, zoom and drag. It decides what renders:
  - A collapsed cluster draws as one bubble showing its size (in auto mode every type counts; in manual mode only the chip-enabled types). Click it to expand: the view zooms in on it. Drag it to move the whole disc (anchored like a node).
  - A cluster expands automatically when its disc is at least `EXPAND_PX` (110px radius) on screen and inside the viewport, nearest the centre first. It collapses below `COLLAPSE_PX` (80px), or when it moves well out of view. That hysteresis, plus a sticky bonus for already-open clusters, stops it thrashing. A clicked-open cluster lapses once the zoom drops below 60% of the zoom it was opened at.
  - **Hard budget:** at most `nodeBudget` (default 400) concept nodes render individually. Clusters claim the budget in priority order. The first one that doesn't fit opens partially: its members nearest the centre render, and the rest fold into a dashed "+N" bubble on its hull. Everything after it stays collapsed. An expanded cluster draws a faint dashed hull with its title.
  - The selected concept, its neighbours and the click-focus reveal set always render, even inside a collapsed cluster. Selecting or searching for a hidden concept pans and zooms far enough for its cluster to open.
  - Detail tiers: the 160 rendered nodes nearest the viewport centre draw in full (label and halo). Nodes further out draw as smaller marks with no label. Off-screen nodes are not in the DOM.
  - Edges are mapped to whatever represents each endpoint: the node, its cluster's bubble, or an off-screen "ghost" at its known position. Duplicates are aggregated. An aggregated edge draws as up to 5 parallel strands, with a weight label from 2 links up. Edges with no on-screen drawn end are dropped. The edge set is capped at 1500, keeping edges that touch the selection first.
- **Edge bundling ("ziptie").** Edges are routed as smooth cubic Béziers, never straight lines. An edge leaves its group (a cluster, or a lone node or bubble) through a gate on the group's footprint, one gate per compass sector (16 of them), chosen by the far group's direction. Edges leaving a group the same way share a gate, so they pinch together there. A cable-tie mark is drawn at gates with 3 or more strands. The strands leave side by side with a small lane gap (never merged into one thick line), ordered so they don't cross, curve to the far group's gate and fan back out to their endpoints. Same-group edges and edges between touching groups draw as gently bowed curves. Arrowheads (typed relations) are chevrons inside the edge's path. Hovering an edge highlights it and raises it above its bundle; the selected node's edges trace through their bundles in the accent colour. Bundles are computed only when the render set or layout changes, or the zoom drifts more than 1.4× (lane gaps and strokes are sized in screen pixels). They are never computed per frame. While the layout is still moving, edges draw straight. In the flat layout the gates come from each cluster's member centroid.
- **Spacing.** Collision radii cover the label as well as the circle: labels are cut to 26 characters, with the full title in the tooltip. Together with stronger repulsion and longer links (flat: charge −800, link distance 170), nodes and labels don't overlap at the default zoom. After the first settle the flat layout zooms out (never below 0.5) if it overflows the viewport.
- **Rendering budget.** Strokes are sized in screen pixels through a `--sw` CSS variable that is refreshed when the zoom drifts. `vector-effect: non-scaling-stroke` is not used: it forced a full re-raster on every pan frame. Nodes use a filter-free halo circle, and the blur filter is kept only for the selected, hovered and focused node. Edges use no SVG markers.
- **Checks.** `node scripts/graph-perf.mjs` prints load, pan, zoom and zoomed-in pan fps for synthetic 500/2k/5k vaults (auto, all types, and all types with bundling off) in headless Chrome with GPU raster. `node scripts/e2e-graph.mjs` covers expand and collapse, the budget cap while panning, detail tiers, select into a hidden cluster, focus, edge hover, bundles and the flat layout. Both run against `bench/graph`: the real `Graph.svelte` over deterministic synthetic vaults (`bench/graph/synthetic.ts`), built standalone and never shipped with the Worker.
- `packages/web` has its own graph frontend (`frontend/graph-view.ts`, local single-user vaults) and does not share this component; it is unchanged.
